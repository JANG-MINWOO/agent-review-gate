---
description: Write the tests that docs/test-audit.md says are missing, with a pin check that rejects tests that don't actually test anything
argument-hint: [optional scope, e.g. "only the top 3" or "src/server"]
---
Turn the audit into tests. Work through **Must create or update before feature work** in `docs/test-audit.md` (run `/review-gate:audit` first if the file does not exist), top to bottom, one module at a time. Respect `$ARGUMENTS` if a scope is given.

For each module:
1. `__RG__ phase test` (tests are the spec; the implement-phase lock is off while you write them).
2. Read the module and its callers. Write tests for the behavior the audit named, in the project's existing test style and runner. Prefer real inputs over mocks; when a dependency must be faked, fake the boundary (network, clock, DB), not the module under test. Do not change production code to make it testable unless there is no test-side way (a `__mocks__` redirect, dependency injection through an existing seam); if you must, keep it minimal, name it in the commit message and the report — it is production change riding in a test commit, and the reviewer must see it as such.
3. Run the new test file with the project's runner. It must pass on the current code — these are characterization tests of existing behavior.
4. Run `__RG__ pin-check --test <test file> --target <source file>`. This blanks the target module and re-runs the test: **it must fail**. If it still passes, the test is not pinning that module — fix the test (assert on real outputs), do not weaken it, and do not move on until pin-check reports `pinned`.
5. Run `__RG__ env-check --test <test file>`. This runs the test with every environment variable the workspace reads set to a dummy value: **it must still pass**. `env-dependent` means the test assumes a variable is absent (VERCEL, an API-URL override…) and will fail on another machine — stub the variable inside the test (`vi.stubEnv`, `monkeypatch.delenv`) rather than relying on the shell.
6. Run the whole suite once (`npm test` or the audit's test command) to make sure nothing else broke.
7. Update the audit file: move the item to a **Done** list with the test file path and the pin-check and env-check results.

When the list is done (or the scope is exhausted): run `__RG__ phase implement`, then `__RG__ review --worktree` once on the new tests (a fresh reviewer checks they assert real behavior and are not tautological). Every `fact` finding — **low severity included** — gets one of two responses in your report: fixed (say what changed, re-run pin-check for that file) or refuted with evidence. Silently leaving one is not an option; a test that pins dead code or re-reads the object it just mutated is exactly what this stage exists to catch. **At most two review rounds**: fix or refute after the first, re-run once, then stop — a reviewer can always find one more low-severity note, and the third round costs more than it catches; list whatever remains as notes in your report. An `unsure` verdict that only says the reviewer could not run something (tests, type-check) is not a reason to re-run: run that yourself, state the result, and treat the review as done. Then report: tests added (file → module), pin-check results, suite status, findings fixed/refuted, what you skipped and why. Do not commit unless the user asked.
